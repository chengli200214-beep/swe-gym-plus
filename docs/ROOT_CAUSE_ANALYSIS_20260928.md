# 未达目标的分层归因、验证与改进

日期：2026-09-28。对象：最新 post-gate 7B LoRA 与三题 Base/SFT pilot。

## 结论

当前直接瓶颈不是训练吞吐，而是 Agent 在定位、读取和失败恢复阶段停滞，未进入有效修改。
向上追溯，已确认 **上下文重复处理导致实际输入与日志不一致**，以及 **训练与部署协议、动作覆盖不一致**。
更上层的流程缺口是：原训练准入侧重格式、来源和 loss，没有充分验证运行时行为契约。

本轮已完成证据拉取、离线复现、输入传递修复和训练准入防回归。
**尚未执行修复后的真实 GPU 复测，不能宣称修复率提升，不能宣称项目目标达成。**

## 2. 从结果向上追溯

| 层次 | 直接证据 | 当前判断 |
|---|---|---|
| 目标/结果 | Base 0/3、SFT 0/3；六次均无补丁，因此候选独立测试未实际启动 | 不是“六个补丁都写错”，而是都没有走到补丁阶段 |
| 行为 | 重复搜索、读取或协议错误耗尽；没有有效 edit | 先检查定位→读取→修改的行为转换，不应只继续降低训练 loss |
| 工具与反馈 | 搜索要求已知文件路径，模型反复猜不存在的路径；长字符串被用于字面搜索 | 工具可运行不等于模型能正确规划使用；路径发现和工具语义需专门验证 |
| 上下文 | 59 请求中 8 个在适配层被再加工，其中 5 个丢掉提醒 | 已复现的实现缺陷；日志有提醒不代表模型看到了提醒 |
| 训练契约 | 230 shell command + 20 done；结构化 search/read/edit 目标均为 0；部署系统提示不同 | 已确认训练/部署分布错位；其对修复率的因果贡献仍需单变量实验 |
| 训练目标覆盖 | 无 Protocol result 恢复样本、无 Harness 提醒样本；任务数仅 20 | 缺少当前失败状态下的恢复监督；不是单纯增加 epoch 可以解决的已知问题 |
| 实验流程 | 用结构与掩码审计代表“对齐”；缺乏训练前行为覆盖门禁；源码存在未提交漂移 | 需要冻结完整行为契约与实际源码，再训练和比较 |

这里的“向上归因”不是把所有失败归给一个 bug。输入传递缺陷、训练分布缺口、模型定位能力
可以同时存在。修复其中一个后仍失败，不足以证明该缺陷不存在，也不应继续原样重复训练。

### 2.1 六次运行到底停在哪里

| 任务 | Base | SFT |
|---|---|---|
| 4787 | 10 步，全为 search；重复后退出 | 6 步，全为 search；重复后退出 |
| 4895 | 15 步，10 search + 5 read；无修改 | 9 步，6 search + 3 read；无修改 |
| 5020 | 13 步，6 search + 5 read + 2 非法动作 | 6 步，4 search + 2 非法动作 |

4787 反复猜 `moto/dynamodb2/models.py`；4895 找到定义附近后仍反复读很小范围；5020
未从入口模块继续定位实际实现。虽然 shell 发现路径的能力仍可用，模型没有成功转换到该动作。

5020 的 SFT 两次非法响应均正好用满 2048 completion tokens：模型把越来越长的
正则式样文本写入字面搜索字段，最终 JSON 不完整。现有证据不支持“放宽 JSON 解析或继续
加大生成上限就能解决”；执行截断命令尤其不可取。

### 2.2 上下文缺陷：已完成反事实输入验证

旧路径：Runtime 选择上下文 → 记录该上下文 → LocalHFModel 再次选择 → 渲染/生成。

`last-action-v2` 遇到协议拒绝时暂时保留两轮；该拒绝离开窗口后，第二次处理可能又退回
只保留最新动作。于是必要历史、工具元信息和当前提醒再次变化。

使用原 tokenizer 和捕获源码回放：

- 59/59 次重建的实际 prompt token 数与原运行记录吻合。
- 8/59 次的消息内容被适配层再次改变；5/59 次丢掉原本已记录的提醒。
- 日志记录上下文直接 token 化只有 54/59 次与实际 prompt token 数相同。
  其余三次内容变化未改变 token 数，说明只比较长度不足以证明输入一致。
- 独立大输出回归还发现 Runtime 在工具输出超过 16000 字符时提前再做一次策略处理：
  两次模型请求触发了三次上下文选择。该冗余路径也已删除。

改进后：Runtime 在请求边界选择一次；适配层原样渲染与计数；有界策略不在工具完成后再跑。
离线 spy 回放 59/59 次输入完全相等，26 次含提醒的请求全部原样传递。
spy 不生成真实模型输出，这只能证明输入通路修复，不能证明模型将接受提醒。
其中 SFT 的 4787、5020 未发生本次检测到的二次上下文变化，仍然失败；因此该缺陷
不能单独解释全部失败。不得把它描述成“找到了唯一原因，修掉就必然提升”。

历史 `last-action-v2` 第一次选择本身仍可能丢弃旧证据/部分提醒；本轮没有暗中改写它的实验含义。
现有 `recent-history-v3` 必须作为单独变量复测，而不是改完默认值后把新成绩与旧成绩直接混比。

### 2.3 训练不等于学会部署行为

原数据并非完全没有代码编辑：230 个 shell 目标中，有命令式修改和测试。
真正缺失的是当前部署的结构化 search/read/edit 协议及相关观察、拒绝恢复样本。
不能将“0 个 typed edit”误写成“0 个任何形式的修改”。

250/250 条系统提示与最新部署不一致；虽然策略标签同为 `last-action-v2`，这不足以证明对齐。
原 tokenizer 回放确认：最长样本 3856 tokens，监督 token 总数 28181，最长目标 1079 tokens；
4096 上限下没有截断，监督后缀正确，历史 assistant 被屏蔽。**本轮没有发现标签掩码或截断错误。**

现有 loss 是训练集平均 loss，不是开发集 loss；配置未提供 eval_file。
不能据此断言泛化已提升，也不能仅凭少量优化步断言一定欠拟合。先做小训练集可学习性诊断，
再区分“监督信号不对”“模型没学会”和“学会但无法泛化”。

## 3. 本轮改动及验收

1. `adapters/model.py` 删除二次上下文筛选；计数与生成使用同一输入。
2. `runtime.py` 只在模型请求边界执行有界策略，避免大输出路径额外执行；不改变工具权限、
   重复动作阈值、独立判分或任何旧成绩。
3. 更新直接调用模型的诊断脚本与观测脚本，使调用方显式负责上下文。
4. 新增 `training/readiness.py`，在 aligned-SFT 入口验证：部署提示 hash、明确策略、
   next-action 掩码声明、来源通过声明、动作键去重、逐 run 结束动作、typed 动作及拒绝后
   改变动作的最低覆盖。检查失败在进入训练器/GPU 前返回。
5. 新增针对实际丢失情景的输入回归、Runtime 单次选择回归、15 项训练准入测试。

对实际旧 250 条数据，准入器拒绝原因：250 个系统提示不匹配，缺少 search/read/edit
目标，缺少明确拒绝后的改变动作样本。旧数据和权重保持原状，不将提示字符串替换后冒充新数据。

新配置必须显式声明 `deployment_prompt_policy`、`deployment_system_prompt_sha256`，并在
实际部署主机上从 `AgentRuntime._system_prompt()` 计算 hash。跨 Windows/Linux 不能沿用
不同平台的系统提示。覆盖门槛只是必要条件，不证明来源真实、数据充分或任务无泄漏。

验收记录：

- 本轮全量迭代回归：**295 passed、12 skipped、0 failed**，540.97 秒。
  跳过项为 Windows 不支持的 Linux 进程组、NsJail、flock、符号链接及显式实机检查。
- 全量进程启动后又补充了 Runtime 单次选择修复，因此上述全量结果不覆盖该末轮补丁。
  末轮补丁另在新进程执行最终定向回归：**38 passed、0 failed**，32.13 秒，
  含 Runtime、模型输入、动作上下文和训练准入；JUnit 收据在私有诊断目录
  `targeted-verification.xml`。上线前仍需最终合并版 Linux 全量回归。
- 两个新输入路径回归均在修复前先失败、修复后通过；真实请求回放 59/59 保真。
- 248 个下载文件的 SHA256 复核 **0 不匹配**。`git diff --check` 通过。
- 使用真实旧配置和 250 条样本运行训练入口，已在准入阶段拒绝，未进入训练。

本轮未使用本机 GPU或外部 API。

本轮改动只在本机工作区，尚未推送 GitHub或部署回 AutoDL；已有用户未提交改动均保留。
云端更新后的源码快照单独保留，下一次同步必须逐项合并，不能用当前较旧的本地目录覆盖云端。

## 4. 下一轮：用最小实验区分原因

| 顺序 | 操作与唯一主要变量 | 观察/停止条件 |
|---|---|---|
| D1 | 固定现有权重、任务、提示、seed、预算，只部署输入传递修复；先跑 4895 一题 | 完整记录模型实际输入；是否读到实现、发出合法 edit、生成补丁；即使无提升也保存结果 |
| D2 | 同一题同一权重，仅将 last-action-v2 改为 recent-history-v3 | 重复拒绝后能否改变动作、利用已读源码；计入增加的上下文/token 成本 |
| D3 | 若仍只搜不改，在公开源码范围做“原导航 vs 提供已观察位置”的定位诊断 | 仅用真实目录/源码观察，不给 gold patch/隐藏测试；标为受辅助诊断，不计自主解决率或训练数据 |
| D4 | 冻结最终工具/提示/上下文；在 train-only 任务采集或真实重放同协议成功轨迹 | read→edit→验证→done、有真实回执；含真实错误恢复；修复导出器对 protocol_rejection 的处理，不造历史 |
| D5 | 用少量训练任务做可学习性探针，再决定正式 7B LoRA | 能否在已见状态输出有效修改/停止；若连训练内行为都学不会，检查数据/优化而非直接扩数据 |
| D6 | 正式训练后，固定预算进行 Base/SFT 公平对照 | 全新且准入通过的任务，排除所有已使用任务；如实报告通过率、成本、失败类型与不确定性 |

每轮最多引入一个主要行为变量，固定结束条件。不同时换服务器、模型、工具、数据和生成上限，
否则结果无法归因。D1/D2 只用于开发诊断；已用 pilot 三题不得再宣传为未曝光最终测试集。

统一拆分指标：

- 找到真实实现路径的任务数；取得有效源码观察的任务数。
- 合法 edit 尝试数、实际执行 edit 数、非空补丁数。
- 收到重复拒绝后改变动作的比例（分母只计实际看到该提醒的请求）。
- 自主正常结束数、独立测试通过数，两者分别报告。
- 每任务 wall time、模型生成/输入 tokens、工具次数与失败原因。

## 6. 引用分析后的追加核查与修正（同日，离线）

本节补充原报告，不覆盖历史实验。原 6535 报告中的 `autonomous_success=true`
同时伴随 `status=failed`、`diff_present=true` 和独立评测 `passed`。
这是**补丁验证成功**，不是**一次正常结束的 Agent 运行**。新报告分别记
`patch_verified`、`run_completed`、`autonomous_success` 和最终补丁哈希；
原冻结门槛“至少一个自主产生的补丁独立通过”仍按 `patch_verified` 判定，
不回写旧报告，也不把这个案例计入干净结束的修复率。

用捕获的 59 条请求和原 7B tokenizer 从消息渲染到最终 token ID 重建：
旧路径的 token 数 **59/59** 与记录一致；重复上下文筛选让 **8/59** 条请求的
最终 input ID 序列不同。修正路径能在渲染后的输入中保留原有运行时提醒。
诊断输出 `../diagnosis-20260928/final-input-verification.json` 只存哈希、长度和
标记位置，不存完整题面或工具输出。这比比较消息对象/长度更强，但仍是
**离线 tokenizer 回放**，不是实际 7B 生成，更不能证明修复率提升。

六条轨迹的最早持续阻塞也并不相同：4787 的 Base/SFT 均反复猜不存在的
`moto/dynamodb2/models.py`；4895 已定位 `moto/dynamodb/models.py` 并读到
`create_table` 或 `Table` 附近，却没有跨入编辑；5020 停留在入口文件及空搜索，
SFT 最后两次输出触及 2048 token 上限且 JSON 无效。不能把这三类失败都
归结为“提醒没传到”，也不能仅以加数据量或换 GPU 作为修复。

追加发现新数据链也有一处独立缺陷：旧 `prepare_aligned_sft.py` 对运行器已选定的
`context_messages` 再调用 `prepare_context`，可能重现双重筛选；且遇到
`protocol_rejection` 就无法导出后续恢复动作，而准入器要求至少一个这样的样本。
现改为只导出带 `runtime-once-v1` 标记、提示策略与部署提示一致的真实输入；
工具动作必须匹配真实回执，拒绝动作不作为目标；无标记的旧事件拒绝冒充
修正后的输入。协议拒绝消息明确记 `executed:false`，供恢复覆盖审计使用。
这修复的是**未来样本导出能力**，没有为过去 250 条样本伪造历史。

原数据中 230 条 shell 目标、20 条 done；其中有启发式识别出的 shell 编辑，
因此“无 typed edit”不等于“完全没有改代码示范”。本机没有原始 20 条成功轨迹
全部事件，也没有 LoRA 权重；无法在本轮重新认证所有成功回执或证明评测时
adapter 已实际加载。训练 loss、配置和摘要只能证明训练流程的部分事实。

下一步按一个变量一轮来判别：固定权重/三题/预算，先在 4895 对比旧与单次筛选
输入能否完成“已读实现→合法 edit”；再单独测试保留更长必要历史。对 4787/5020，
只提供真实已观察到的路径/源码位置做**辅助定位诊断**，不计自主通过或训练数据。
另做已知动作的受控重放，验证工具协议和写盘，再采集 train-only 的同协议轨迹。
Base 在三题 0/3 **不是**小规模训练可学习性探针的前置禁令；只要来源与协议
审计通过，可先用少量真实样本测已见状态的动作模仿，再做正式 LoRA 与全新
未曝光任务对照。最终分别报告有效编辑、非空补丁、独立通过和正常结束。

AutoDL 实例仍按用户上次要求保持关闭。本节没有启动 GPU、付费 API 或训练。
