## 归因边界与下一步

本轮进一步确认：在这一题上，单独修复输入传递、增加历史、或给出一个真实文件位置，都不足以触发有效修改。D3 的“提示可见但未被使用”把怀疑重点推向动作选择/工具语义与训练-部署协议错位；它不证明 7B 一般地不会修复，也不能从一个复用任务估计修复率。由于服务器、运行代码及若干工具提示相较旧 pilot 也发生变化，D1 不能被宣称为对旧成绩的纯单变量因果比较；D1→D2、D2→D3 才是同一新环境内的逐项对照。

下一步应优先做更小的行为探针：在同一固定权重与任务上，用真实的、已确认的源码回执构造“已读到相关实现”的受辅助续跑，观察模型能否输出合法 edit；同时对 Base 与 LoRA 用同一输入做短对照。若连已见源码状态都不能稳定编辑，先检查协议目标和训练样本覆盖，不重复训练旧 250 条错位样本。只有补齐真实 read→edit→验证→done 及失败恢复轨迹并通过训练准入后，才启动新 LoRA；正式效果仍需全新、未曝光、独立准入的留出任务。

本轮没有调用 DeepSeek API、没有使用本机 GPU、没有向公开仓库上传私有轨迹或权重。云端轨迹和权重仍缺独立外部备份；按用户先前选择暂不做外部备份，保留这一单点风险。服务器仍开机，空闲也可能计费。

归因因此细化为：在这道题上，提供真实相关源码后，“不产生任何编辑”已不再是唯一障碍；现在直接可见的是**补丁语义错误与编辑后验证/纠错不足**。旧 LoRA 的注释式补丁尤其提示训练目标与真实修复行为可能错位，但单题不能证明微调总体退化。下一轮应先审计训练样本中的真实 `read → edit → test → done`、失败反馈恢复及补丁语义，剔除无效/注释式动作，冻结同一协议后再训练；之后在未曝光任务上做公平 Base/SFT 独立对照。云端 GPU 已回到空闲，实例仍开机可能计费。
